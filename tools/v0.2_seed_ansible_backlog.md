## What's still NOT covered (true completeness gaps)

If the goal is "agent never goes to web for ansible," these remain:

1. **Common errors / troubleshooting catalog** (~20-30 synthesized claims). Things like "Authentication failure (SSH)", "sudo password is required", "ansible_python_interpreter not found". These don't have clean canonical URLs — they'd need synthesized claims with multi-source evidence (Stack Overflow, Red Hat KB, docs.ansible.com troubleshooting page).

2. **Workflow-level recipes** (~15-20 claims). "How to deploy a Django app with ansible", "Bootstrap RHEL/CentOS", "Rolling deployment with serial". These are *playbook patterns* that exist as docs pages but require curation from blog posts + the official guide.

3. **Tower / AWX / Automation Platform.** Red Hat's orchestration product. Has its own doc site (`docs.ansible.com/automation-controller/`). ~20-30 claims if added.

4. **The 22 known URL failures above** — fix by mapping to actual locations.

5. **Filter plugin pages** — only `json_query_filter.html` was attempted (and failed). Common filters (default, mandatory, regex_search, dict2items, items2dict, b64encode, password_hash, hash, to_yaml, to_json, etc.) deserve their own claims. ~20 entries.

These four gaps total ~80-100 more claims for absolute completeness. The 95th-percentile common case is already covered.

## What's needed to make this actually USEFUL to agents

Per the conversation, the content is in place. The matcher needs the embeddings + re-rank upgrade for high-confidence answers to clear the SDK's `is_useful` ≥ 0.6 gate. Without that, the 439 claims surface at the right lexical match but at 0.45 confidence — agents using `is_useful` to gate on quality will still escalate to web search.

**Sequencing:** matcher upgrade first, then the remaining 80-100 claims to close the absolute completeness gap.
